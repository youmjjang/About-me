PROJECT 03 / PERSONAL실제 Nginx 로그 지속 감시 · 대시보드

PERSONAL · 로그 수집부터 보고까지

Mini SOC

탐지 다음의 과정까지
하나의 흐름으로.

오탐 보완

시간창 없는 탐지를 줄이다

Password Spraying을 단순 다계정 누적이 아니라 300초 안에 서로 다른 계정 3개 이상 실패한 경우로 제한했습니다. Brute Force는 초 단위 시각도 처리하도록 보완했습니다.

실시간성

한 번 읽고 끝나는 데모에서 지속 감시로

기존 sample_server.log 1회 분석 외에 live_monitor.py를 추가해 실행 이후 새로 생기는 로그만 읽고, 동일 경보는 5분 쿨다운으로 반복 알림을 줄였습니다.

실행 범위와 AI 활용 방식 보기

샘플 데모: sample_server.log의 이벤트 11건에서 HTTP Error, Brute Force, Password Spraying, Night Login 규칙으로 6개 경보가 생성되도록 구성했습니다. HIGH 경보는 승인 후 block_ip 대응을 시뮬레이션합니다.

실제 로그 확인: Docker Nginx를 8081 포트로 실행하고 run_live.py logs/access.log로 지속 감시했습니다. 존재하지 않는 경로 요청으로 404 로그를 만든 뒤 http_error → watch → POST /alert 201 → 대시보드 반영 순서를 확인했습니다.

범위: 계정 잠금과 IP 차단은 실제 시스템 변경이 아닌 시뮬레이션입니다. LLM API가 없거나 실패하면 규칙 기반 fallback을 사용하며, Slack Webhook이 없으면 알림 단계만 건너뜁니다.

수치 구분: 샘플 로그 11건에서 나온 경보 6건과 화면의 누적 사건 13건은 서로 다른 집계입니다. 누적 화면의 사건 수를 한 번의 샘플 분석 결과로 해석하지 않습니다.

PROJECT 04 / PERSONAL모바일 실제 실행 화면

PERSONAL · 위치 기반 웹앱

쉬엄쉬엄

지금 있는 곳 주변에서
잠시 쉴 자리를 찾습니다.

현재 위치나 검색한 장소를 기준으로 벤치·쉼터·공원 후보를 지도와 목록에 보여주고, 선택한 장소까지의 보행 경로를 안내하는 반응형 웹앱입니다.

  • OpenStreetMap

직접 사용하며 발견한 장소 누락, 한글 자동완성, 검색 순서 문제를 수정하고, Render에서 Vercel로 배포 환경을 옮기며 실제 서비스 화면과 API 응답을 확인했습니다.

설계 판단장소 데이터에 착석 여부나 이용 가능성이 명시되지 않으면 확인이 필요한 후보로 구분합니다. 경로 계산이 실패했을 때 직선거리를 보행 거리처럼 표시하지 않습니다.
사용하면서 발견한 문제와 개선 과정 보기

기능을 구현한 뒤 실제 검색과 이동 흐름을 확인하면서, 사용자가 기대한 결과와 다르게 동작하는 부분을 찾아 수정했습니다.

1. 바로 앞의 정류장이 검색에서 빠지는 문제

의자가 있다고 등록된 정류장만 찾는 조건 때문에, 실제로 쉴 수 있어도 좌석 정보가 없는 정류장은 후보에서 빠졌습니다. 좌석 미확인 정류장도 검색에 포함하고, ‘의자 확인됨’과 ‘좌석 확인 필요’를 구분했습니다. 데이터에 정보가 없다는 이유로 장소 자체를 제외하지 않되, 실제 착석 가능성을 확정해서 보여주지 않도록 판단했습니다.

2. 엔터를 눌러야 나타나는 것처럼 보였던 장소 후보

한글 입력이 조합 중일 때는 자동완성 요청을 막는 조건이 있었습니다. 입력 도중에도 후보를 검색하도록 바꾸고, 두 글자 이상 입력한 뒤 250ms 동안 추가 입력이 없으면 요청하도록 조정했습니다. 새 입력이 들어오면 이전 요청을 취소하고, 오래된 응답이 현재 검색어의 목록을 덮어쓰지 않도록 요청 순서도 확인합니다.

3. ‘대전시청역’보다 주변 가게가 먼저 나오는 문제

TMAP에는 역이 ‘시청역[대전1호선]’으로 등록되어 있어, 단순한 이름 비교에서는 ‘대전시청역점’이 포함된 가게가 더 관련 있는 결과로 정렬됐습니다. 역 유형과 지역명·노선 정보를 함께 비교해 ‘대전시청역’ 검색을 해당 역과 연결했습니다. 실제 응답으로 역이 첫 번째에 오는지, 다른 지역의 동명 역이나 특정 가게 검색을 잘못 우선하지 않는지 확인했습니다.

4. 배포 환경을 옮긴 뒤 디자인이 사라진 문제

Render에서 사이트 접속 대기를 겪은 뒤 Vercel로 이전했습니다. 첫 배포에서는 HTML만 표시되고 CSS·JavaScript 파일이 404로 응답했습니다. Node.js 서버 배포에 정적 파일이 포함되도록 설정을 추가하고, 화면 파일과 장소 검색·주변 시설 검색·도보 경로 API가 정상 응답하는지 확인했습니다. 이전 후 포트폴리오의 실행 링크도 새 주소로 맞췄습니다.

5. 지도와 목록의 역할에 맞춘 화면 조정

버스정류장은 파란 정류장 핀, 나머지 휴식공간은 초록 벤치 핀으로 구분했습니다. 마스코트를 로고와 앱 아이콘에 적용하고, 제목에는 둥근 서체를 사용했습니다. 본문과 목록은 로컬에서 비교한 뒤 기존 서체를 유지해 장소명·거리·안내를 읽기 편하도록 조정했습니다.

개선하며 배운 점: API가 정상 응답하는 것만으로 검색 경험이 완성되지는 않았습니다. 실제 입력 방식, 사용자가 부르는 장소명과 데이터의 등록명 차이, 배포 후 파일 제공 여부까지 확인해야 원하는 결과로 이어진다는 점을 배웠습니다.

데이터와 화면 범위: OpenStreetMap과 TMAP의 외부 정보를 사용하며, 장소의 실제 좌석 상태·무료 이용·개방 여부는 현장 확인이 필요합니다. 위 아이폰 화면은 당시 목록·보행 경로 실행 기록이며, 이후 변경한 핀과 서체까지 반영한 최신 화면은 아닙니다.

해결하려는 문제: 가까운 곳에 짐을 맡겨도, 회수하러 돌아가는 길 때문에 전체 이동이 길어질 수 있습니다.

구현 흐름: 보관과 회수를 포함한 네 구간의 대중교통·도보 경로를 합산하고, 보관 없이 이동하는 경로와 비교해 우회시간을 보여줍니다.

사용자 선택: 전체 이동시간과 짐을 들고 이동하는 시간을 함께 보고 일정에 맞는 보관함을 고를 수 있도록 구성했습니다.

보관 정보 보호: 브라우저의 Web Crypto API를 사용해 PBKDF2로 키를 유도하고 AES-GCM 방식으로 보관 정보를 암호화해 로컬 저장소에 보관합니다.

공동 개발·검증: 이틀 동안 두 명이 역할을 엄격하게 나누기보다 함께 기능을 구현하고, 서로의 작업을 점검하며 오류를 수정했습니다.
